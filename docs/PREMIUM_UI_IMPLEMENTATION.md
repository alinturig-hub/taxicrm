# Premium TaxiCRM UI implementation

The approved design is applied as graphite navigation, ivory content and petrol actions, with a small champagne brand accent. Light is the default; the header theme control offers dark and persists the choice in browser localStorage. No theme preference is written to the database. Public authentication screens share the palette; standalone refusal pages use the light workspace tokens.

`workspace-theme.css` owns semantic colours and a scoped compatibility layer for existing slate/blue utilities. This avoids replacing source text or backend/status identifiers throughout the codebase. Sidebar tokens remain graphite in either theme. Existing inline map marker/chart-series colours are retained. Legacy state colours map to success/warning/danger text, primary buttons keep white text, and reduced-motion preferences are respected. The legacy dark token definitions in globals.css are overridden by the new stylesheet imported after it.

Navigation now has Today, Operations, Customers, Marketing and Performance, followed by a visual separator for Integrations and Configuration. Business overview is retained at /dashboard under Performance. Automation is grouped under Configuration. All destination routes and permission-filtered navigation remain; configuration and received webhook histories are still distinct. Login now opens /dashboard/workspace, while /dashboard remains the business overview for existing links.

Today uses live stored counts with explicit definitions: indexed pickupDueTime records in the Europe/London day; stored individual customer profiles; stored driver profiles; and recorded FAILED webhook events. Queries run only with the corresponding view permission. Pickup records with no known pickup time are excluded. Counts do not claim driver availability, completed bookings, revenue or connection health. Next-step links use existing workflows. No prototype/demo numbers, incident ownership, due dates or campaign-send functions were added.

Validation uses synthetic loopback data and blocked external browser requests. Production build and navigation tests pass. Chromium verifies light/dark colour/persistence, permission filtering, module search, marketing/customer flows, configuration navigation, mobile drawer/focus and redirects; additional smokes cover English authentication, Local JSON imports and webhook configuration. No real SMS, real import, backfill, finance-rule change or schema migration is required.
