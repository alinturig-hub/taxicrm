# SMS gateway and freephone notifications

Implemented on `codex/taxicrm` after explicit approval of the four new tables and their production migration on 11 October 2026. Earlier proposal documents describe the previous preview-only version.

## Configuration

Open Configuration → SMS Gateway. Save the signed Orion URL (first save only), sender and field names. Secrets are AES-256-GCM encrypted using the existing integration key; the public API returns only the base URL and credential-presence flag. Saving sends no SMS. Gateway defaults disabled. To send a real test, save and enable the gateway, enter an explicit destination/message and press Send real test SMS. Tests are persisted and processed by the worker, with a stable request ID preventing accidental resubmission.

Use **Add** for each freephone. Enter its display name, a manually entered general SMS recipient, the exact Autocab source field/value and event rules. Each event can override the recipient and has its own text; threshold is explicit. Source candidates are BookingSource, BookedBy, OurReference and TelephoneNumber for an explicitly verified freephone line. Ordinary customer numbers are never automatically classified as freephones. Preview current count reads the booking aggregate without sending. Verify the field/value actually identifies the freephone before enabling; values not observed in stored bookings cannot be enabled. If the actual source is another payload field, a verified mapping adapter is still needed; do not choose an unrelated field.

The first check follows a full configured window after creation, activation or source/window changes. A 12-hour inactivity window uses minute checks; legacy/default 24-hour windows use daily checks. Times are displayed Europe/London; DST does not change elapsed hours. After downtime, the current rolling window is checked; missed periods are not replayed as old SMS alerts. Windows are `(now-window, now]`, using the provider's bookedAtTime. Future bookings are excluded. Missing source/date data suppresses zero/threshold alerts; daily reports carry an incomplete-data warning. Periodic events retain their daily cadence. An inactivity event creates one message per continuous episode; a new booking rearms it and cancels inactivity messages still pending/retrying. Disabling a workflow cancels pending/retry messages; a request already in flight cannot be recalled.

## Worker and delivery history

The authenticated internal worker endpoint runs each minute through the existing CRON_SECRET scheduler, planning at most five workflows and processing at most ten messages per tick. Job rows and delivery rows are claimed with transaction row locks and SKIP LOCKED, across replicas. Counts, logical run identity, messages and next schedule are saved atomically. Unique run and event/destination constraints prevent duplicates. This does not guarantee exactly-once physical delivery by a provider without idempotency support.

ACCEPTED means HTTP/provider acceptance, not confirmed handset delivery. HTTP 429 retries have a bounded delay and five-attempt cap. Other rejections fail. HTTP 5xx, interrupted calls, oversized acknowledgements and expired sending leases become UNCERTAIN and are not blindly resent. The administrator can inspect history and reconcile with Orion; no automatic resend of uncertain messages is implemented. Provider response bodies, signed URLs and credential values are not logged or exposed as errors.

The gateway and workflows can be disabled independently. A disabled gateway performs no new planning or delivery. Disabling and re-enabling the gateway retains the queue; review pending messages before re-enabling. Booking reads are SQL aggregates, without loading whole payload histories into Node. Counts have a 10-second statement timeout. Latest 30 checks and up to 100 workflows are displayed.

## Approved deployment migration

`20261011190000_sms_notifications` is additive: only SmsGatewayConfiguration, NotificationJob, NotificationJobRun, NotificationDelivery, their indexes/relations and its Prisma migration-history entry. It does not modify Booking, financial rules or existing records.

For this approved rollout, ENABLE_SMS_SCHEMA_MIGRATION=true makes startup execute only this migration inside one transaction and an advisory lock. It checks the checksum of any completed migration and fails closed on conflicting/incomplete history. It does not invoke the full historical migration chain. ORION_SMS_BOOTSTRAP_ENCRYPTED can initialize an absent gateway with the signed parameters encrypted for the production integration key; the gateway remains disabled and no jobs/recipients are created. Existing gateway settings are never overwritten by bootstrap. These bootstrap variables should be removed from saved runtime configuration after successful rollout; repeated execution is idempotent.

Verification uses only an isolated database, synthetic recipients and mocked Orion requests. No real SMS is sent during development verification. Production schema changes are authorized; real sending is activated only by the administrator's configured workflows or explicit test button.

Verified freephone line numbers can explicitly use TelephoneNumber as their source. UK national, +44 and 0044 formats are normalised. The read-only lookup accepts at most 25 supplied lines and returns aggregate counts plus three booking examples per line; it does not create workflows or send SMS. Missing booking dates and future dates are reported separately. The monitored line is separate from the SMS recipient.

The inactivity event supports an explicit 12-hour rolling window (new form default), with minute checks after a full 12-hour activation grace period. Existing unspecified windows remain 24 hours with daily checks. A persistent state transition creates one alert per continuous inactivity episode; observing a booking rearms it. Missing dates/source data suppress alerts. Periodic reports and threshold checks retain a 24-hour cadence and 24-hour counts. State transitions and daily checkpoints are retained instead of writing a history row on every minute check. The worker plans at most five due jobs per minute, so multiple lines can introduce a few minutes of delay. All booking statuses count as line activity. This detects possible freephone or booking-feed issues, not a proven hardware fault.

## Freephone activation and canonical evidence (12 October 2026)

Booking monitoring now reads the existing mapped bookedAtTime first. If absent, it can use only the original rawPayload.BookedAtTime with an explicit ISO timezone and a calendar-valid PostgreSQL timestamp. Missing mapped telephone numbers can use the original rawPayload.TelephoneNumber. These fallbacks are read-only: they do not backfill Booking, change payloads, substitute pickup/import/received dates or alter financial calculations. PostgreSQL 16+ pg_input_is_valid is required (the isolated environment uses 17 and the configured production database uses 18).

Lookup displays the last 12-hour count, remaining missing dates, verified original timestamp use and feed source gaps. Future creation timestamps, unidentified current sources and missing dates block inactivity activation and are shown explicitly in Preview. An enabled workflow can still become blocked if data quality deteriorates; the worker suppresses uncertain alerts. The preview inspects the selected 12-hour rule even while its event is disabled. A mapped timestamp takes precedence over payload timestamps, preserving existing normalised records.

Disabled draft imports accept 1–25 explicitly supplied name/phone pairs. A transaction/advisory lock makes repeated imports idempotent and preserves existing workflows, recipients and enabled state. Created drafts have no SMS recipient, no enabled event, no confirmed source and no enabled workflow. The admin UI offers this import; the service-key protected /api/internal/freephone-setup endpoint exposes only the same disabled provisioning operation and cannot activate delivery. SMS configuration and message sending remain separate administrator actions.

The first selected line is Derriford Main Entrance (07766387614); the user will enter its SMS recipient manually. Configure the recipient, confirm the mapped line, enable the 12-hour inactivity event and the workflow only after Preview shows booking evidence ready. The gateway must be enabled separately. No real SMS or booking backfill is performed as part of verification.

Verification passed: 42 unit tests, 30 synthetic integration tests, build/type/lint checks, authenticated HTTP checks and a local Chromium journey covering persisted drafts, canonical payload evidence, explicit manual recipient/source/event activation and the 12-hour grace period. The source Booking rows and original payloads remain unchanged.
